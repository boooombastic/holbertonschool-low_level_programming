# Green Efficiency and Software Performance Analysis

## Measurement Methodology

All timing measurements were collected in C using the standard `<time.h>` library (`clock()` and `CLOCKS_PER_SEC`), capturing processor time consumed by the executing process and formatting outputs to six decimal places (`%.6f` seconds). To account for runtime variance caused by operating system scheduling and background system activity, each experiment was executed three consecutive times without modifying the core algorithmic logic or input datasets. In `baseline_loop.c`, a deterministic loop of `100,000,000` iterations was measured using a `volatile` accumulator to prevent compiler dead-code elimination. In `comparison_algorithms.c`, two functions counting even integers over a static array of `50,000` elements were timed independently within the same process. Finally, in `instrumentation_lab.c`, nested `clock()` boundaries isolated three sequential execution phases (`build_dataset`, `process_dataset`, and `reduce_checksum`) alongside an outer `TOTAL` timer wrapping all three phases.

## Observed Performance Differences

The recorded execution times demonstrate how algorithmic complexity dominates runtime performance. In `comparison_algorithms.c`, the quadratic naive implementation (`count_even_naive`, $O(n^2)$) required `2.764242` seconds, `2.801612` seconds, and `2.770523` seconds across three runs, yielding an average of `2.778792` seconds. By contrast, the linear single-pass implementation (`count_even_single_pass`, $O(n)$) completed the task in `0.000107` seconds, `0.000105` seconds, and `0.000106` seconds, averaging `0.000106` seconds. The quadratic approach was approximately `26,215` times slower than the single-pass approach because it performed roughly $1.25 \times 10^9$ inner-loop checks instead of `50,000`. In `instrumentation_lab.c`, phase-level profiling over `50,000` integers recorded a `TOTAL` time of `0.000744` seconds, broken down into `0.000283` seconds for `BUILD_DATA`, `0.000320` seconds for `PROCESS`, and `0.000135` seconds for `REDUCE`. The `PROCESS` phase consumed the largest share of runtime (`43.0%` of total execution) due to integer division and modulo operations per element, while `TOTAL` (`0.000744` seconds) remained greater than the sum of individual sub-phases (`0.000738` seconds) because it encompasses all three stages plus intermediate `clock()` call overhead.

## Relation Between Runtime and Energy Consumption

CPU execution time directly correlates with dynamic energy consumption because active processor cycles keep execution units, memory buses, and caches in high-power states. When `count_even_naive` executes for `2.778792` seconds instead of `0.000106` seconds, the processor core remains actively occupied for over `26,000` times longer to solve the exact same problem size. Eliminating redundant iterations and expensive arithmetic instructions reduces active CPU cycles, allowing the processor to finish work rapidly and transition back into low-power idle states, thereby lowering total joules consumed per computation.

## Limitations of the Experiment

Several experimental constraints affect precision. First, `clock()` measures CPU time at microsecond-level resolution (`CLOCKS_PER_SEC`), which introduces quantization noise for sub-millisecond phases like `count_even_single_pass` (`0.000106` seconds) and individual phases in `instrumentation_lab.c` (`0.000135` to `0.000320` seconds). Second, calling `clock()` six times around short phases adds minor instrumentation overhead (`0.000006` seconds) to `TOTAL`. Third, static array sizes (`50,000` integers, or ~200 KB) fit comfortably within modern CPU L2/L3 caches, masking main-memory latency bottlenecks that occur with larger datasets. Finally, no direct hardware power meter or RAPL energy counters were used, so energy savings are inferred from active CPU duration rather than measured in watts.

## Practical Engineering Takeaway

Algorithmic optimization is the primary lever for both software speed and energy efficiency. Before tuning micro-optimizations or upgrading hardware, engineers should analyze asymptotic complexity and instrument distinct execution phases to locate true hotspots. Replacing an $O(n^2)$ algorithm with an $O(n)$ single-pass design reduced runtime by four orders of magnitude, proving that selecting the right algorithm and avoiding redundant operations yields the highest return in performance and sustainable resource usage.
